# 基于 UOS Kernel 的 Agentic AI 应用

> 日期: 2026-05-06

## Agent 与 Kernel 的关系

Agent 不维护自己的世界模型 — 它直接从 Kernel 获取。

```
感知: Watch / Read / History   → Agent 看到世界发生了什么
推理: 基于孪生时间线 + 拓扑    → Agent 理解为什么、会怎样
执行: Write / RCtl / Relate   → Agent 改变世界状态
```

每个 Agent 应用本质上是**一段在世界模型上运行的策略逻辑**，类似操作系统上的进程。

## 应用一：根因聚合 Agent

**问题**：一次主网故障级联出上百张重复工单（实测数据中 1 分钟内产生 117 张）

**策略**：
```
Watch(所有终端, "status=offline")
  → 短时间内同馈线/同变电站多台离线
  → Traverse(终端, UP, contains) 找到共同上游
  → History(上游设备) 确认是否有故障事件
  → Write(根因工单, "关联设备: N台") 合并为一张
  → 对已生成的重复工单: Write(重复工单, status=merged)
```

**价值**：117 张单 → 1 张根因单，运维人员不再被淹没。

## 应用二：智能诊断 Agent

**问题**：85% 的工单最终靠"重启"解决，但人需要 4.5 小时才接单

**策略**：
```
Watch(工单, "status=created")
  → Read(工单) 获取缺陷类型和设备
  → History(设备, 近90天) 查看历史故障模式
  → 判断:
      若 历史3次同类 且 都是重启解决 → 建议更换
      若 首次出现 且 类型=程序卡死   → 自动远程重启
      若 同馈线多台                  → 转根因聚合
  → Write(工单, "diagnosis", "程序卡死，建议远程重启")
```

**价值**：从"人到现场才知道原因"变成"秒级自动诊断"。

## 应用三：自动消缺 Agent

**问题**："终端在线率"类工单（占 46%）中大部分只需远程重启

**策略**：
```
Watch(工单, "diagnosis=可远程处置")
  → Open(目标终端)
  → RCtl(终端, "remote_restart", {})
  → Watch(终端, "status=online", timeout=10min)
  → 若恢复:
      Write(工单, status=repaired, cause="远程自动重启")
    若超时:
      Write(工单, status=escalated, cause="远程重启无效，需现场")
      → 转派单 Agent
```

**价值**：46% × 85% ≈ 39% 的工单可自动闭环，无需人工介入。

## 应用四：智能派单 Agent

**问题**：当前按区域固定派人，不考虑负载和技能匹配

**策略**：
```
Watch(工单, "status=created" AND "需现场")
  → Traverse(工单, located_at → 设备 → 所属区域)
  → Traverse(区域, contains → 人员)
  → 对每个候选人员:
      Read(人员) → 当前负载
      History(人员, 今天) → 今日已处理量
      匹配: 人员技能 vs 缺陷类型
  → 选择最优人员
  → Relate(工单, 人员, assigned)
  → Write(工单, status=accepted)
```

**价值**：从"固定分配 4.5h 响应"到"智能匹配 < 5min 响应"。

## 应用五：预测性维护 Agent

**问题**：设备反复故障才换，而非提前预防

**策略**：
```
定时扫描:
  → All(终端)
  → 对每台终端: History(终端, 近180天)
  → 特征提取:
      故障频率、同类型故障次数、上次维修距今天数
  → 若 故障频率上升 且 同类型≥3次:
      Write(终端, "health", "degrading")
      创建预防性工单: Write(新工单, type="预防性维护")
      Relate(新工单, 终端, located_at)
```

**价值**：从"坏了再修"到"快坏时主动换"。

## 应用六：知识沉淀 Agent

**问题**：解决方案散落在工单自由文本里，无法复用

**策略**：
```
Watch(工单, "status=archived")
  → Read(工单) 获取: 设备型号、缺陷类型、原因、解决过程
  → 从解决过程中提取结构化知识:
      设备型号 + 故障模式 → 标准处置步骤
  → Open/Write(知识条目资源)
  → Relate(知识条目, 设备型号, applies_to)

被诊断 Agent 引用:
  → Traverse(设备型号, inbound, applies_to) → 找到适用知识
```

**价值**：经验不再只存在某个人脑子里，新人也能获得专家级判断。

## Agent 协作模式：共享黑板

```
┌─────────────────────────────────────────────────────┐
│                Agent 应用层                           │
│                                                      │
│  根因聚合 ─→ 智能诊断 ─→ 自动消缺                    │
│                 ↓              ↓                     │
│            智能派单        预测维护                    │
│                 ↓                                    │
│            知识沉淀 ←─────────────────┘              │
│                                                      │
│  每个 Agent 都通过 ROSIX 读写同一个世界模型           │
│  Agent 之间通过世界模型的状态变化间接协作             │
├──────────────────────────────────────────────────────┤
│                UOS Kernel                             │
│   资源 + 数字孪生 + 拓扑 + ROSIX                     │
└──────────────────────────────────────────────────────┘
```

**关键设计**：Agent 之间不直接通信，而是通过世界模型的状态变化间接协作。

- 诊断 Agent 写入 `diagnosis` 字段 → 消缺 Agent Watch 到后行动
- 消缺 Agent 写入 `status=escalated` → 派单 Agent Watch 到后接管
- 所有 Agent 的行为自动记录在孪生时间线中 → 可审计、可回溯

这是**黑板架构**（Blackboard Architecture）：世界模型就是共享黑板，Agent 是知识源（Knowledge Source），状态变化是触发条件。

## 数据验证

以上所有策略均基于真实数据验证可行性：

| Agent | 数据支撑 |
|-------|----------|
| 根因聚合 | 244 次批量事件（≥5单/分钟），最大一次 117 单 |
| 智能诊断 | 前三大根因占 60%+，模式高度可识别 |
| 自动消缺 | "程序卡死"类占 591 单，消缺中位数 < 3 分钟（=远程重启） |
| 智能派单 | 41 人覆盖 9 区域，负载极不均衡（最高 653 单 vs 最低 < 50 单） |
| 预测维护 | 同一设备最多出现 8 次工单，存在明显退化模式 |
| 知识沉淀 | 4643 条解决过程文本，44 种缺陷原因可归类 |
